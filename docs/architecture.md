# YPuddinImageBox 技术方案

> 状态：M0 进行中（2026-09-27）
> 目标平台：Windows 10（1803 及以上）/ 11，macOS 12 及以上（Apple 芯片与 Intel）
> 界面：夜幕画廊，8 套内置配色（颜色源文件 `src/theme/themes.json`）

## 1. 结论

**Tauri 2 + React / TypeScript（界面）+ Rust（下载、图库、缩略图）**，本地数据用 SQLite。

## 2. 选型对比

| | Tauri 2（推荐） | Electron | Python 打包（PyInstaller + pywebview） |
|---|---|---|---|
| 安装包体积 | 约 10–20 MB | 约 100 MB 以上 | 约 60–120 MB |
| 常驻内存 | 低，适合挂在托盘里跑订阅 | 高 | 中 |
| 界面渲染 | Windows 用 WebView2（Chromium 内核），macOS 用系统 WKWebView（Safari 内核），两端都要测 | 两端同一个 Chromium，最一致 | 同 Tauri |
| 下载内核 | 用 Rust 重写训练器的 booru 模块 | 用 TypeScript 重写 | 直接复用训练器的 Python 代码 |
| 打包、签名、自动更新 | 官方打包器 + updater 插件 | electron-builder，成熟 | 最麻烦，Windows 上杀毒软件误报常见 |
| 主要代价 | 需要写 Rust | 体积和内存 | 分发体验差，要带整套 Python 运行时 |

选 Tauri 的理由：

1. 夜幕画廊本来就是网页技术画的（CSS 变量主题、毛玻璃、瀑布流），Tauri 可以原样实现，主题 CSS 直接复用。
2. 软件要常驻托盘跑订阅，还要管理几万张图的索引和缩略图，Rust 在内存占用和并发下载上更合适。
3. 训练器的下载内核规模不大（搜索、字段归一、令牌桶、退避、重试），用 Rust 重写成本可控。
4. 前端沿用训练器那套 React + TypeScript + Vite，写法和组件经验都能复用。

备选：如果更看重「全部用 TypeScript、两端渲染完全一致」，可以用 Electron，代价是安装包和内存大得多。不建议走 Python 打包路线。

## 3. 架构

```
┌─────────────── 前端（React + TypeScript） ───────────────┐
│ 发现 / 图库 / 订阅 / 队列 / 设置   主题：themes.css 变量   │
└──────────────┬──────────────────────────▲───────────────┘
      命令（invoke）                  事件（进度、日志、限速状态）
┌──────────────▼──────────────────────────┴───────────────┐
│                     Rust 核心（Tauri）                    │
│ sources  Booru / Kemono 适配器（统一接口：搜索、计数、帖子解析）  │
│ net      HTTP 客户端（描述性 UA、代理）、双令牌桶、429/503 退避   │
│ jobs     下载队列（持久化、暂停/继续/取消、重启后续跑）、订阅调度 │
│ library  SQLite 索引、md5 去重、缩略图缓存、导出训练集          │
│ protocol 自定义图片协议：本地缩略图与远程预览统一经 Rust 加载   │
│ secrets  API Key 存系统钥匙串                                  │
└──────────────────────────────────────────────────────────┘
```

几个关键设计：

- **远程图片不让界面直接请求**。瀑布流里的远程预览图也经过 Rust 下载和缓存，这样代理、UA、限速和域名白名单只有一处；训练器的画廊代理就是这么做的。
- **队列持久化**。任务和进度写进 SQLite，软件重启后能接着下载。
- **API Key 不写明文**：默认存进系统钥匙串（Windows 凭据管理器、macOS 钥匙串），也可以选择加密后存进设置文件（XChaCha20-Poly1305，密钥由本机设备标识和随机盐经 HKDF 派生，文件复制到别的电脑解不开）。
- **超出 tag 上限自动本地过滤**。Danbooru 免费账号一次只能搜 2 个 tag（Gold 6 个、Platinum 12 个），多出来的条件在拿到结果后本地筛。实测 `rating:`、`date:`、`score:` 不占额度，排除项（`-tag`）和 `order:` 占额度；`order:` 无法在本地等价实现，超额时只能提示。

## 4. 存储位置

四类目录都能在「设置 → 存储」里改：

| 位置 | 放什么 | 默认位置 | 修改后 |
|---|---|---|---|
| 图片 | 下载的原图 | 系统「图片」文件夹下的 YPuddinImageBox | 立即生效；可移动已有图片，或留在原处 |
| 数据库 | 图库索引、下载任务、订阅 | 软件数据目录下的 database（随软件数据一起移动） | 重启后生效；可移动，或改用新位置里已有的数据库 |
| 软件数据 | 设置、日志 | 系统应用数据目录下的 data | 重启后生效；可移动，或新位置从空开始 |
| 缓存 | 缩略图、预览图 | 系统缓存目录下的 image-cache | 立即生效；可移动，或清空旧缓存 |

规则：
- 位置设置本身写在系统配置目录的 `storage.json`，位置固定，软件靠它找到其余目录。
- 数据库、软件数据运行中一直被占用，修改时先记为待迁移，下次启动时在打开任何文件之前搬完；失败则保持原位置并在界面上提示。
- 新位置不能和其他任何一类位置重叠（默认数据库在软件数据目录里除外）；选择移动时新位置必须是空文件夹。
- 同一磁盘直接重命名；跨磁盘先复制并核对大小，再删除旧文件。
- 系统 WebView 自己的缓存不在管理范围内，默认缓存目录用了单独的子文件夹，移动或清空时不会碰到它。

## 5. 技术清单

**前端**
- React + TypeScript + Vite，包管理用 pnpm
- TanStack Query 处理命令调用的数据，Zustand 管界面状态
- 虚拟化瀑布流：按列计算位置，只渲染可视区域
- 界面语言：中文、英文，用自己写的小翻译函数，不引入 i18next（做法见「进度」）
- 样式：Tailwind CSS（和训练器一致），颜色全部映射到主题变量
- 字体：Manrope 随安装包内置，中文用系统字体（苹方 / 微软雅黑）
- 动效：Motion for React 负责组件进出场和视图切换；悬停、按下等微交互和图片加载扫光（Shimmer）用 CSS；换主题优先用 View Transitions API 整窗淡入，不支持时退回颜色渐变。时长 120–250ms，遵守系统「减弱动态效果」

**Rust**
- tokio（异步运行时）、reqwest（HTTP，rustls，带 SOCKS 代理支持）
- governor 或自写令牌桶（限速）
- sqlx（SQLite 与数据库迁移）
- image + fast_image_resize（缩略图）、md-5（去重）
- keyring 4（系统钥匙串：macOS 钥匙串 / Windows 凭据管理器）、tracing（日志）

**Tauri 插件**
- updater（自动更新）、autostart（开机启动）、single-instance（只开一个实例）
- window-state（记住窗口位置）、notification（订阅有新作时通知）、dialog、opener
- 托盘用 Tauri 内置的托盘功能

## 6. 数据模型

已实现（`src-tauri/migrations/0001_library.sql`，数据库文件 `library.sqlite3` 放在「数据库」位置）：

- **posts**：已下载的帖子。来源 + post_id 唯一，md5 建索引；本地路径存绝对路径，图片位置整体移动时一起改写，选「已有图片留在原处」时保持不变。Kemono 的一个帖子有多个图片附件时，每个附件使用稳定的派生 post_id。
- **tags / post_tags**：tag 按名称合并、两个站点共用；Gelbooru 的 tag 不带分类，已有具体分类的 tag 不会被改回「一般」
- **jobs**：下载任务。类型（选中的帖子 / 按条件下载全部结果）、查询串、上限、状态、计数、下一页的页码参数
- **job_items**：任务里的每张图（帖子信息 JSON、结果、跳过或失败的原因），重启后从未完成的项继续
- **subscriptions**（`0002_subscriptions.sql`）：来源、tag、分级、查询串、检查间隔、是否启用、已处理到的最大 id、上次检查时间和结果；jobs 表加 `subscription_id` 关联检查任务
- **posts.posted_at**（`0004_posted_at.sql`）：帖子发布时间（Unix 毫秒）。两个站点 `created_at` 的格式不同（Danbooru 是 ISO 8601，Gelbooru 是 `Sat Sep 27 01:02:03 -0500 2026`），由程序解析后写入，旧记录在打开图库时补上；图库按上传先后排序用

- **saved_searches**（`0006_saved_searches.sql`）：收藏的搜索条件（来源、tag、分级、排序），同样的条件只存一份；只用来重新搜，不自动下载。来源是按固定顺序、逗号分隔的站点（例如 `danbooru,gelbooru`，有两个以上时是聚合搜索）；`0007_saved_search_sources.sql` 把上一版存的 `all` 换成了这种写法

下载规则：

- 保存到 `图片位置/站点/画师/帖子id.扩展名`，没有画师 tag 时直接放在站点目录下；文件夹名去掉 Windows 和 macOS 不允许的字符
- 已在图库中、或图库里已有 md5 相同的图时跳过；视频和动图压缩包暂不下载
- 边下载边算 md5，大小和 md5 对得上才改名成正式文件；网络错误、5xx、校验不通过最多试 3 次
- 一次跑一个任务，任务内最多 4 张同时下载；暂停、取消会中断进行中的下载并删掉临时文件
- 按条件下载时边翻页边下载：Danbooru 默认排序用「id 小于某值」翻页，指定了 order: 时按页码；未登录时站点会隐去部分帖子，所以取到空页才算翻完
- 缩略图宽不超过 480、高不超过 1440，存在「缓存」位置的 thumbs 目录，删掉后浏览图库时重新生成
- 删除时和移动图片位置互斥；移不进废纸篓的文件保留记录并报告原因，文件本来就不在的直接删记录

## 7. Windows 与 macOS 的差异

- **窗口标题栏**：macOS 用 Overlay 标题栏，红黄绿按钮嵌进左侧栏顶部；Windows 隐藏系统标题栏，右上角自绘最小化、最大化、关闭，顶部留拖拽区。
- **半透明**：Windows 11 可选云母效果，macOS 可选毛玻璃，默认关闭。
- **快捷键**：⌘ 和 Ctrl 自动对应。
- **默认目录与路径**：按平台区分（下载目录、缓存目录、配置目录）。
- **测试**：你在 Mac 上开发，Windows 版在 CI 上构建，另外需要一台 Windows 机器或虚拟机实测界面。

## 8. 打包与发布

- **Windows**：NSIS 安装包（.exe），内置 WebView2 引导安装。没有代码签名证书时，首次运行会弹 SmartScreen 提示，可以之后再买证书。
- **macOS**：.dmg，通用二进制（Apple 芯片 + Intel）。暂不购买 Apple 开发者账号，GitHub Actions 直接生成未签名安装包，首次打开由系统提示用户手动允许。
- **自动更新**：tauri-plugin-updater，更新包单独签名，托管在 GitHub Releases。
- **CI**：GitHub Actions 分别在 Windows 和 macOS 机器上构建。

- **M0 技术验证**：两端跑通空壳；Rust 客户端带 UA 和代理访问 Danbooru / Gelbooru，确认能过 Cloudflare；自定义协议加载远程预览；主题切换。
- **M1 可用版本**：搜索与估算、下载队列（限速、退避、重试、取消）、SQLite 图库与 md5 去重、图库浏览、设置（账号、代理、存储、外观）。
- **M2**：订阅与增量下载、托盘常驻与新作通知、超出 tag 上限的本地过滤、导出训练集（图片 + .txt）。
- **M3**：安装包、自动更新；训练集导出和更多来源另行安排。

## 10. 要尽早验证的风险

- **Cloudflare**：训练器的经验是按 UA 放行，但 Rust 客户端的 TLS 指纹和 Python requests 不同，M0 先用真实账号验证。
- **两端渲染差异**：WKWebView 和 WebView2 在毛玻璃、字体、滚动上有差异，要在两个平台都测。
- **图库规模**：已压测（2026-09-27，见「进度」）。十万张时图库查询都在 40 ms 以内，瀑布流只渲染看得见的卡片，加载到几千张也保持 60 帧。图库首页的文件夹约 30 ms，按画师、作品、角色分组 90～120 ms；按一般 tag 分组要把每张图的 tag 全部过一遍，0.75～1 秒，是目前最慢的一处，图库再大就要缓存。

- 已完成：存储位置设置（四类目录、迁移、重启后生效、目录重叠和非空检查）。
- 已完成：SQLite 图库与 md5 去重、下载队列（暂停、继续、取消、重试失败项、重启后续跑）、按条件下载全部结果（先统计数量、可设上限）、图库浏览（按 tag、来源、分级筛选）、发现页多选下载。

- 已完成：图库里删除图片（移到废纸篓 / 回收站，或只移除记录；macOS 上用 NSFileManager，不需要「控制访达」权限）、图库和发现页多选、文件不见了时标出并可以重新下载。

**M2 进行中**：
- 已完成：订阅与增量下载。订阅记下「已处理到的最大 id」，检查时建一个从这个 id 往新的方向翻页的下载任务（Danbooru 用 `page=a<id>`，Gelbooru 用 `id:>N sort:id:asc`），每取一页就在同一个事务里推进这个 id，中断后从断点继续；没找到新图的检查任务自动删掉，下载到新图时发系统通知。条件里带 order: / sort: 排序的不能订阅。
- 已完成：后台运行。菜单栏（Windows 为托盘）图标可以打开窗口、立即检查订阅、退出；关闭窗口时默认在后台继续运行，可在「设置 → 通用」改成退出；开机启动（带 `--background` 参数，启动后不弹窗口）。
- 实测：订阅起点设在第 3 新的帖子，检查一次正好找到比它新的 2 张并推进到最新的 id；检查进行中不会重复建任务。
- 已完成：超出 tag 上限的本地筛选。Danbooru 按账号等级算上限（未登录 2、Gold 6、Platinum 以上 12；`rating:`、`date:`、`score:` 不计数），超出时带冒号的条件和前几个要「有」的 tag 交给站点，其余（含排除项、`*` 通配）在本地按每个帖子的 tag 筛选；搜索每次最多往下翻 5 页凑够一页，下载任务和订阅把本地筛选条件存进数据库，翻页位置仍按站点的整页推进。计数接口不限 tag 数量，所以估计的总数仍然准确。站点报的上限比算出来的小时，按站点给的数字重拆一次。
- 实测：未登录搜「1girl scenery sky」直接请求会被拒；拆成站点「1girl scenery rating:g」+ 本地「sky」后一页 200 条筛出 90 条，全部带 sky。
- 已完成：条件排序和复选下拉框。发现页可按最新 / 最早上传、分数排序，Danbooru 另有收藏、近期热门（`order:rank`，只含最近两天左右）、分辨率、文件大小；Gelbooru 只支持前三种，换站点时不支持的排序回到默认。排序条件占一个 tag 额度，选了排序改按页码翻页；输入框里手写的 order: / sort: 以下拉框为准。「下载全部结果」按所选排序取前 N 张；订阅按上传先后找新图、不带排序；统计张数时不带排序（Danbooru 带 order:score 这类条件时不给数字），近期热门除外。图库可按下载时间、发布时间、分数、收藏、分辨率、文件大小排序。分级筛选从四个胶囊合并成复选下拉框（第一项「全部」，至少保留一项，连着勾选时停 300 毫秒再搜）。
- 界面：全应用的下拉框（搜索框里的来源、筛选行的分级和排序、订阅间隔）统一成一个组件，菜单放在浏览器顶层（popover），不会被对话框或滚动区域裁掉，支持方向键、回车、Esc；对话框里按 Esc 只收起菜单。
- 实测：未登录时「scenery rating:g」加各种排序都在 2 个 tag 以内，翻两页（共 40 条）顺序都接得上（`cargo run --example probe`）。
- 性能测试（Apple M 系列、release 构建）：`cargo run --release --example library_bench` 造 10 万张（每张约 25 个 tag，tag 频率长尾分布）。写入每张约 1 ms，数据库约 100 MB。改造前按 tag 筛选要 110～380 ms（每个帖子逐一检查），改成从 tag 一侧查、页内只按 id 排序后，所有排序和筛选组合都在 40 ms 以内（冷门 tag 1 ms、热门 tag 33 ms、排除热门 tag 21 ms、分级加来源 11 ms）。另外：去掉 `WHERE 1 = 1` 后 SQLite 才会用排序列的索引；统计信息不能抽样（来源、分级这种低区分度的列会被误判）；首次分析 10 万张约 0.3 秒，只在数据变化很大时才重做。
